# Rust AutoWipe — плагин автовайпов для панели Catalyst (catalystctl)

Плагин панели **Catalyst** для игры **Rust**: расписание вайпов + выбор каталогов и файлов,
которые удаляются при вайпе, с остановкой и запуском сервера через API панели,
предупреждениями в чате и историей прогонов по шагам.

Проверено по документации Catalyst (релиз **v1.89.0**, ноябрь 2026) и исходникам
`catalystctl/catalyst`. Номер версии плагина — поле `version` в `rust-autowipe/plugin.json`,
что в ней изменилось — в начале `CHANGELOG.md`. В комплекте: исходники плагина, собранный
пакет `dist/rust-autowipe-<version>.catpkg.zip`, индекс маркетплейса и тесты.

---

## 1. Что выяснилось про плагины Catalyst (кратко и по делу)

Панель Catalyst — TypeScript-панель + Rust-агент на нодах + containerd. Плагин панели —
это **не мод игры**, а расширение самой панели: он исполняется **в процессе backend**
(Node.js), поэтому получает доступ к API панели, файловому туннелю и БД в рамках
объявленных разрешений.

Ключевое из документации:

| Возможность | Как выглядит для плагина |
|---|---|
| HTTP-роуты | `/api/plugins/<name>/…`, та же сессия/API-ключ, что и у панели |
| Вкладки и страницы | админ-вкладка, вкладка сервера, отдельная страница, слоты |
| Планировщик | `ctx.scheduleTask('* * * * *', fn)` — 5-польный cron, живёт в процессе, умирает при выключении плагина |
| События | `server:started`, `server:stopped`, свои события |
| Хранилище | key-value + коллекции документов (JSON-документы в БД панели) |
| Файлы сервера | `ctx.fileTunnel.queueRequest(nodeId, op, serverUuid, path, data)` — операции `list`, `download`, `upload`, `delete`, `rename`, `compress`, … |
| Права | `permissions` (плагину) и `userPermissions` (ролям панели) |

Важные ограничения, которые определили архитектуру:

1. **Плагин работает в процессе панели.** Ошибка в коде может уронить backend;
   изоляция (`runtime: "isolated"`) не реализована и отклоняется загрузчиком.
2. **Нет прямой возможности «остановить/запустить сервер».** В контексте плагина есть
   только чтение `servers`/`users`, файловый туннель, WebSocket и планировщик. Power-действия
   в панели — отдельные REST-роуты (`POST /api/servers/:id/start|stop|restart|kill`),
   поэтому плагин ходит в них сам, со своим API-ключом.
3. **Фронтенд маркетплейс-плагина — самодостаточный ESM-бандл** `frontend/frontend.mjs`
   (панель отдаёт его по `/plugins-assets/<name>/frontend.mjs`). В нём **не работают React-хуки**:
   у бандла своя копия React, диспетчер хуков не установлен. Поэтому UI плагина —
   обычный DOM внутри React-обёртки (см. §7).
4. **Установка** — только через маркетплейс (`.catpkg.zip` + sha256) или копированием
   каталога в `PLUGINS_DIR` (`/var/lib/catalyst/plugins` в контейнере `catalyst-backend`).
   Код попадает на диск **выключенным**; включение требует принятия дисклеймера безопасности.
5. **`scheduleTask` не переживает перезапуск панели** — задачи регистрируются заново в
   `onEnable`. Поэтому состояние расписания хранится в коллекциях, а не в таймерах.

Источники: [Plugin Development](https://docs.catalystctl.com/api/plugins/),
[Plugin Backend](https://docs.catalystctl.com/api/plugins/backend/),
[Plugin Frontend](https://docs.catalystctl.com/api/plugins/frontend/),
[Packaging & Marketplace](https://docs.catalystctl.com/api/plugins/packaging/),
[Admin → Plugins](https://docs.catalystctl.com/admin/plugins/).

## 2. Что делает плагин

### Привязка к серверу и яйцу

Плагин — **серверная вкладка**, а не панельная: она объявлена как
`location: 'server'` с фильтром по шаблону:

```js
templateFilter: { namePattern: 'rust' }
```

- Панель показывает вкладку только внутри сервера, чей шаблон (яйцо) матчится этой
  регуляркой (без учёта регистра): «Rust», «Rust Dedicated Server», «Rust (Oxide)» и т.п.
- Если шаблон назван иначе, поправьте `namePattern` в
  `rust-autowipe/frontend/frontend.mjs` и `RUST_TEMPLATE` в начале
  `rust-autowipe/backend/index.js` (backend проверяет имя шаблона по тому же правилу),
  пересоберите пакет (`python tools/pack.py`) и обновите плагин.
- Все backend-роуты имеют вид `/api/plugins/rust-autowipe/servers/:serverId/…`.
  Перед обработкой плагин проверяет доступ к серверу: админ панели, владелец сервера
  или субпользователь из списка доступа этого сервера (кто что может — §5.2).
- **Только Rust.** Backend сам спрашивает у панели имя шаблона сервера (своим API-ключом)
  и отказывает серверу, у которого в имени нет `rust` (без учёта регистра): ответ `403`
  «Сервер не Rust…». Плановый вайп такого профиля пропускается, причина сохраняется
  в профиле (`lastSkipReason`). Если имя шаблона узнать нельзя (нет API-ключа, панель
  не ответила), проверка пропускается: вкладка и так видна только у серверов Rust.
- Профили и история прогонов хранят `serverId`; чужой профиль нельзя прочитать,
  изменить или запустить через роут другого сервера.

### Сид и размер карты

В блоке «Карта» профиля задаётся, что делать с переменными `WORLD_SEED` и `WORLD_SIZE`
перед запуском сервера:

| Параметр | Режимы |
|---|---|
| Сид (`WORLD_SEED`) | не менять · случайный каждый вайп · фиксированный · по списку по очереди |
| Размер (`WORLD_SIZE`) | не менять · фиксированный (1000–6000) · случайный из набора |

- Значения записываются через `PATCH /api/servers/:id/variables` **после остановки**
  сервера и поиска путей, **до удаления** файлов; затем сервер стартует и Rust генерирует
  мир заново. Если поиск путей упал или упёрся в предел, переменные не меняются.
- Если удалять нечего (ни один путь не найден), сид и размер всё равно меняются — так
  решил владелец. Прогон при этом считается ошибкой, сервер, остановленный плагином,
  поднимается.
- Режим «по списку» хранит курсор в профиле (`mapState.seedCursor`); курсор двигается
  только после успешной записи, поэтому пропущенный/упавший вайп не «съедает» сид.
- Плагин пишет только сид и размер. В имени переменной сида должно быть `SEED`, в имени
  переменной размера — `SIZE`, и это две разные переменные; иначе сохранение даст ошибку.
  Если в старом профиле указана другая переменная, вайп пишет в `WORLD_SEED` и `WORLD_SIZE`.
- Кнопка **«Определить из шаблона»** читает список переменных сервера через панель и
  подставляет найденные `*SEED*` / `*SIZE*` (по умолчанию `WORLD_SEED` / `WORLD_SIZE`).
  Значения вкладка получает только у этих переменных, у остальных — одни имена: среди
  них бывают пароли (например, RCON).
- **Dry-run** ничего не пишет: в истории видно, какие значения были бы заданы.
- При ошибке записи (нет права `server.startup`, правило шаблона не пропустило значение)
  вайп **прерывается до удаления файлов**, а остановленный сервер поднимается обратно.
- У профилей, созданных до 1.2.0, поля `map` нет — для них сохраняется прежнее поведение
  («не трогать карту»), чтобы обновление плагина не меняло мир. Карточка пишет
  «сид не меняется · размер не меняется», и сохранение из редактора этого не меняет.
- Через API поле `map` — объект с `seed` и `size` (или поля нет вовсе). Строка или число
  вместо него — ошибка 400.

### Расписание (требование 1)

Четыре типа расписания. Время — **в часовом поясе профиля** (поле «Часовой пояс», имя IANA,
например `Europe/Moscow`). Пояс не выбран — время в поясе панели (TZ контейнера backend):

| Тип | Пример | Для чего |
|---|---|---|
| `weekly` | еженедельно, четверг 05:00 | обычный недельный вайп карты |
| `monthly_nth_weekday` | **первый четверг месяца**, 19:00 | вайп под Force Wipe Facepunch |
| `monthly_day` | 1-е число, 06:00 | фиксированное число (в коротких месяцах поджимается к последнему дню) |
| `interval` | каждые 7 дней, 05:00, от точки отсчёта | произвольный цикл |

Как это работает:

- у профиля хранится `nextRunAt`;
- перевод часов в поясе профиля: несуществующее время (весной) переносится на момент
  перевода (02:30 → 03:00), из двойного (осенью) берётся первое. Без пояса профиля — по
  часам панели: несуществующее 02:30 → 03:30, из двойного — первое. Если перевод приходится
  на полночь (так бывает в Гренландии), сдвигается один запуск, а серия «каждые N дней»
  идёт дальше по своим дням;
- раз в минуту планировщик (`ctx.scheduleTask('* * * * *')`) ищет профили с `nextRunAt <= now`.
  Выключатель `schedulerEnabled` действует сразу, перезапуск не нужен: выключен — нет ни
  вайпов, ни предупреждений;
- опоздание считается целыми минутами. Если оно больше `catchUpMinutes` (по умолчанию 120),
  вайп **не** запускается «задним числом», а сразу переносится на следующую дату. Время и
  причина пропуска сохраняются в профиле (`lastSkippedAt`, `lastSkipReason` в ответе
  `GET …/profiles`) и пишутся в журнал панели; в истории прогонов пропуска нет.
  `catchUpMinutes: 0` — пропущенное не догонять, но вайп в свою минуту идёт.
  Не число или меньше 0 — считается как 120;
- после прогона следующий срок считается по серии от планового времени (а не от конца
  вайпа); сроки, которые уже прошли, пропускаются;
- если панель перезапустилась — при включении плагина просроченные профили добираются
  в пределах окна catch-up. Сначала игроки получают обычный отсчёт в чате, и вайп идёт
  через `wipeWarningMinutes` минут. Если отсчёта не будет (предупреждения выключены, нет
  API-ключа, это проверка), вайп идёт сразу. Ручной вайп во время такого отсчёта отменяет
  догон.

«Каждые N дней» считаются от точки отсчёта (даты): вайп в эту дату, через N дней, через
2N и т. д. Если точку отсчёта не задать, плагин ставит её сам при сохранении — день
сохранения в поясе профиля (пояс не выбран — в поясе панели). У старого профиля без точки
отсчёта (если расписание не меняли) ею становится дата его ближайшего планового запуска,
и серия не сдвигается.
Дата видна в редакторе в поле «Точка отсчёта». Правки профиля, «Выключить» и «Включить»
серию не сдвигают.
Пример: точка отсчёта — понедельник 02.11, шаг 7 дней → 02.11, 09.11, 16.11…; профиль
выключили в среду и включили через неделю — серия та же.

Неверные поля расписания — ошибка 400 с причиной (раньше их молча подменяли): вид
(`weekly`, `monthly_nth_weekday`, `monthly_day`, `interval`), время ЧЧ:ММ, день недели 0–6
(0 — воскресенье), неделя месяца 1–4 или -1 (последняя), число 1–31, интервал 1–365 дней,
точка отсчёта ГГГГ-ММ-ДД (настоящая дата) и часовой пояс. Поле, которого нет в запросе,
получает значение по умолчанию, как раньше.

### Выбор каталогов и файлов (требование 2)

- В редакторе профиля — кнопка **«Выбрать в файлах…»**: файловый пикер ходит по реальному
  дереву сервера через `ctx.fileTunnel` (операция `list`), можно отмечать файлы и каталоги
  чекбоксами или добавить текущий каталог целиком. Путь можно вписать и вручную: поле под
  списком «Что удалять» и кнопка «Добавить».
- Поддерживаются **маски** (шаблоны имён):

  | Запись | Что значит | Пример |
  |---|---|---|
  | `*` | любые символы в имени, в том числе ни одного | `/server/*/proceduralmap.*.sav` |
  | `?` | ровно один любой символ | `proceduralmap.*.sav.?` — копии `.sav.1` … `.sav.9` |
  | `**` | любое число папок, в том числе ни одной; только целым звеном пути (между `/`) | `/oxide/**/backup.json` |
  | `[*]`, `[?]`, `[[]` | сама звёздочка, сам вопрос, сама скобка `[` — буквально | `/oxide/data/[*].json` — файл с именем `*.json` |

  Особый смысл есть только у этих трёх записей. Они нужны, когда в имени файла есть `*`,
  `?` или `[`. Выбор в файлах пишет их сам. Любые другие квадратные скобки — обычные
  символы, как в 1.5.6: `Kits[1].json`, `[backup]` значат ровно то, что написано, поэтому
  старые профили смысла не меняют. Обратный слэш `\` для этого не годится: панель
  превращает `\` в `/`. `**` работает и в целях, и в исключениях.
- **Цель, которая кончается на `**`** (например `/oxide/data/**`), — это сама папка
  целиком, как в 1.5.6. Плагин читает только папку, где она лежит (проверяет, не ссылка
  ли это), а внутрь не заходит, поэтому большая папка не упирается в пределы. Если внутри
  есть исключения, подпапки читаются.
- **Исключения** — отдельный список «не удалять». Исключение каталога защищает всё его
  содержимое: если исключён `/server/*/cfg`, то при цели `/server/*` плагин не удалит каталог
  целиком, а спустится внутрь и удалит всё, кроме `cfg`. Сама папка, в которую плагин
  спустился, остаётся (даже если стала пустой). Исключение с `**` (например
  `/oxide/**/keep.json`) защищает файлы на любой глубине, но для этого плагин читает каждую
  папку под целью: на большом дереве так легко упереться в предел запросов (см. ниже).
  Тогда сузьте цель или исключение.
- **Весь корень удалить нельзя.** Цель, в которой нет ни одного обычного символа — только
  `/`, `*` и `?` (`/*`, `/**`, `/**/*`, `/?*`, `/*/**` и т. п.), — это снос всей установки,
  а не вайп. Такую цель профиль не сохранит (ошибка 400). Старый профиль с такой целью
  ничего не удалит и сервер не остановит: плагин проверяет цели до остановки, отменяет
  вайп, причина — в истории. Сохранить такой профиль (даже кнопкой «Выключить») нельзя,
  пока цель не исправлена; удалить — можно.
- **Пределы одного прогона:** не больше 500 путей, 250 чтений папок и 8 уровней
  вложенности. Цель без масок тоже тратит запрос: плагин читает папку, где она лежит, и
  проверяет, не ссылка ли это. Если поиск упёрся в предел, предпросмотр пишет «Список
  неполный» и какой предел сработал, а вайп **не удаляет ничего**: сервер, остановленный
  плагином, поднимается, в истории причина. Сузьте маски или разделите профиль на несколько.
- Если папку прочитать не удалось (агент ответил не «нет такого файла», а, например,
  таймаутом, отказом или «Data directory does not exist»), поиск путей останавливается,
  и вайп тоже ничего не удаляет.
- **Похожее на ссылку не удаляется.** Ссылка (symlink) — это ярлык на другой файл или
  папку. Агент Catalyst удаляет не саму ссылку, а то, куда она ведёт. Отличить ссылку
  плагин может только по правам: у ссылки они всегда 777. Поэтому всё с правами 777 плагин
  не удаляет и внутрь не заходит (ни по `**`, ни при обходе исключений). Так же проверяются
  пути, выбранные в файлах точно.
- **Если среди найденного есть такое, вайп не начинается.** До смены сида и до удаления —
  ошибка со списком таких путей, сервер, остановленный плагином, поднимается. Лучше не
  вайпнуть вовсе, чем вайпнуть наполовину. В предпросмотре такие пути показаны в
  «Пропущено» с пометкой «пока они есть, вайп не начнётся». Если это обычный файл или
  папка с правами 777 (например, после `chmod -R 777`), смените права (644 для файла,
  755 для папки) или уберите путь из профиля.
- **Странные имена тоже останавливают вайп:** имя с `\` или с пробелом в конце. Панель
  меняет такой путь перед отправкой агенту, и удалился бы другой путь. В выборе файлов
  такие имена отметить нельзя; удалите их вручную. Имя с пробелом в начале удаляется как
  обычно.
- **Чего плагин не видит:** ссылку в середине пути (например, если сама папка `/oxide/data`
  — ссылка) и точку монтирования (папку, к которой подключён другой диск или папка хоста).
  Что лежит за ними, удалится как обычное содержимое. Не держите такие папки внутри того,
  что удаляет профиль.
- **Проверка при сохранении** — ошибка 400 с номером элемента (раньше лишнее молча
  отбрасывалось): не больше 40 целей и 40 исключений, путь не длиннее 400 символов,
  нельзя `/` целиком и `..` (выход из папки сервера); не больше 10 команд после запуска,
  каждая не длиннее 200 символов.
- **Предпросмотр** («Что будет удалено») показывает итоговый список путей после раскрытия масок
  и применения исключений — до любого удаления. Папки помечены: папка удаляется целиком,
  со всем, что внутри. Ниже — «Пропущено» с причинами; пока такие пути есть, вайп не
  начнётся.
- **Пресеты** для Rust (см. §6) добавляются одним кликом.

### Порядок вайпа

1. Записать начало прогона в историю. Не вышло и после 3 попыток — вайп не начинается,
   сервер не трогается.
2. Прочитать сервер (`ctx.db.servers`). Сервер приостановлен в панели (в том числе после
   «Из архива», пока приостановка не снята) — отказ: такой сервер плагин не вайпает и не
   проверяет.
3. Если сервер работает — отправить `stop` в API панели. Ответа панели плагин ждёт до
   90 с (ответ 202 значит «принято»); ответа нет — смотрит статус сервера. Затем ждёт
   `stopped` не дольше `stopTimeoutSec`. Уже остановленный сервер не трогаем;
   `error`/`crashed` считаем неработающим. Сервер работает, а остановка в профиле
   выключена — ошибка: на живом сервере файлы не удаляются.
4. Раскрыть цели в конкретные пути (маски → список, исключения, пропуски). Поиск упал
   или упёрся в предел — **ничего не удаляется**, сид и размер не меняются, сервер
   поднимается (см. ниже), прогон — ошибка.
5. Сменить сид и размер карты, если это включено в профиле (ошибка — вайп прерывается
   до удаления). Если удалять нечего, сид и размер всё равно меняются, а прогон — ошибка
   «Ни один путь не найден».
6. Удалить пути через файловый туннель (агент удаляет каталоги рекурсивно). Агент не
   ответил на 3 удаления подряд — удаление прекращается.
7. Если включено «Запускать сервер после вайпа» — отправить `start` (даже если сервер
   стоял ещё до вайпа) и ждать `running` не дольше `startTimeoutSec`. «Запущен» — только
   `running`: в `starting` сервер ещё грузится. `stopped`, `error` или `crashed` после
   запуска — сразу ошибка. Команды в консоль (`console.write` у ключа) уходят только
   после `running`.
8. Дописать итог в историю и в профиль: шаги, ошибки, предупреждения, сколько удалено.

Запись о прогоне появляется в истории в начале вайпа и дописывается по ходу: если панель
упадёт посреди вайпа, след останется. История — не больше 200 прогонов на каждый сервер.

Защита от «полуразобранного» сервера: если сервер остановил **плагин** и после этого что-то
пошло не так (ошибка поиска путей, карты, удаления), плагин всегда поднимает его обратно
и пишет шаг «Восстановление запуска» — даже при выключенной галочке «Запускать сервер после
вайпа»: она только про запуск после удачного вайпа. Подъём тоже ждёт `running`.

Если панель упала или перезапустилась посреди вайпа, при следующем включении плагин
закрывает такой прогон как прерванный («Прогон прерван: …»). Если сервер остановил плагин
и он так и стоит, плагин отправляет команду запуска. Если панель ещё не принимает запросы
или агент не подключился, запуск повторяется раз в минуту — до 60 минут или 30 попыток;
каждая попытка и итог видны в шагах этого прогона. Список удалённых путей у такого
прогона может быть неполным.

Один вайп за раз:

- на одном сервере идёт не больше одного вайпа, даже из разных профилей; второй запуск
  получает ответ 409. Второй профиль на тот же срок пойдёт, когда первый закончится
  (если успеет в окно `catchUpMinutes`), — с отсчётом в чате;
- если плановое время уже наступило или наступило во время ручного вайпа, плановый
  вайп пропускается: срок переносится на следующий. Исключение — ручной вайп упал,
  ничего не удалив: тогда плановый остаётся. Проверка (dry-run) плановый вайп не отменяет;
- профиль нельзя менять и удалять, пока он выполняется (409);
- выключение и перезагрузка плагина идущий вайп не прерывают;
- вайпы разных серверов идут параллельно и друг друга не задерживают.

### Предупреждения в чате

За `wipeWarningMinutes` (по умолчанию 5) до `nextRunAt` планировщик отправляет в консоль
сервера `say …` по одному сообщению в минуту: 5, 4, 3, 2, 1. Текст задаётся
`wipeWarningText` (`{minutes}` → число минут), глобально выключается `wipeWarningEnabled`,
у профиля есть свой чекбокс `options.warnChat`.

Перед проверкой (dry-run профиля или глобальный `dryRun`) отсчёт не отправляется: вайпа
не будет, а игроки бы его ждали. Догон пропущенного вайпа тоже идёт с отсчётом
(см. «Расписание»).

Отправленные отметки лежат в профиле (`warnedRuns`) по времени запуска, поэтому панель
не дублирует сообщения после перезапуска и не повторяет их дважды в одну минуту.
Нужен `console.write` у API-ключа: без ключа или права предупреждения просто не уходят.
Чип «Чат: ок / ошибка» в шапке вкладки показывает последнюю отправку только этого сервера.

Режим **dry-run** — «проверка» (глобально в настройках плагина, галочкой «Только проверка»
в профиле или кнопкой «Проверка» на карточке) ничего не останавливает и не удаляет — только
раскрывает пути и пишет отчёт: что было бы удалено и какие сид и размер были бы заданы.
Итог проверки пишется отдельно (`lastCheckAt`, `lastCheckStatus`, `lastCheckId`,
`lastCheckError`) и не затирает итог настоящего вайпа: на карточке видно и «последний
вайп: …», и «Проверка: ок/ошибка, дата».

## 4. Установка

### 4.1. Вариант A: скопировать каталог (самый быстрый для своего сервера)

Каталог плагинов в контейнере — `/var/lib/catalyst/plugins` (volume `catalyst-plugin-data`).

```bash
# на хосте панели, рядом с распакованным rust-autowipe/
docker cp ./rust-autowipe catalyst-backend:/var/lib/catalyst/plugins/rust-autowipe
docker compose -f /opt/catalyst/catalyst-docker/docker-compose.yml restart backend
```

После рестарта backend делает discovery и находит плагин. Дальше:

**Admin → Extensions → Plugins → Rust AutoWipe → Enable** → принять дисклеймер
(в нём будут перечислены `server.read`, `files.read`, `files.write`).
Затем откройте **сервер с шаблоном Rust** — вкладка **Rust AutoWipe** появится в его
карточке (см. §2 «Привязка к серверу и яйцу»).

> Обновление: скопировать файлы поверх (`docker cp ./rust-autowipe/. catalyst-backend:/var/lib/catalyst/plugins/rust-autowipe/`)
> и вызвать `POST /api/plugins/rust-autowipe/reload` (см. §4.4) либо перезапустить backend.

### 4.2. Вариант B: установка из маркетплейса по URL

Нужен HTTPS-хостинг для архива (GitHub Release, ваш CDN, nginx на том же сервере).

```bash
SHA=$(cut -d' ' -f1 dist/rust-autowipe-<version>.catpkg.zip.sha256)

curl -X POST https://panel.example.com/api/plugins/install \
  -H "Authorization: Bearer $CATALYST_API_KEY" \
  -H 'Content-Type: application/json' \
  -d "{\"url\":\"https://cdn.example.com/rust-autowipe-<version>.catpkg.zip\",\"sha256\":\"$SHA\"}"
```

`sha256` обязателен: панель проверяет дайджест до распаковки, без него — `CHECKSUM_REQUIRED`.

### 4.3. Вариант C: свой индекс маркетплейса (GitHub)

Репозиторий уже является готовым индексом: в корне лежит `index.json`, он ссылается
на пакет в `dist/` ветки `main` по `https://raw.githubusercontent.com/...`, рядом —
sha256 пакета. Панель умеет ставить плагины прямо оттуда — ничего hosted-ить не нужно.
Всё, что попало в `main`, панели видят сразу (см. §4.3a).

1. **Admin → Extensions → Marketplace → Marketplaces → Add**:
   - **URL**: `https://raw.githubusercontent.com/kafder100/RustWipe/main/index.json`
   - **Label**: `RustWipe`
2. Вкладка **Marketplace** → **Rust AutoWipe** → **Install**.
   Панель скачает `.catpkg.zip`, сверит sha256 с индексом и распакует код
   **выключенным** (ничего не исполняется до дисклеймера).
3. **Admin → Extensions → Plugins → Rust AutoWipe → Enable** → принять дисклеймер.
4. **Settings** → `apiKey` (§5.1).

Что важно знать:

- панель кэширует индекс **5 минут**; после публикации новой версии нажмите
  обновление в маркетплейсе — появится **Update**, когда версия в `index.json`
  станет выше установленной;
- `raw.githubusercontent.com` кэширует файлы ещё примерно на 5 минут (заголовок
  `no-cache` этот кэш не пробивает). Сразу после `git push` панель может видеть
  прошлую версию — подождите несколько минут. Пакет новой версии лежит по новому
  URL (`…-<version>.catpkg.zip`), кэша у него нет, поэтому после обновления индекса
  он скачивается сразу;
- при скачивании панель требует **HTTPS** и публичный хост: `raw.githubusercontent.com`
  подходит, локальные/приватные адреса отклоняются (`FORBIDDEN_HOST`);
- sha256 обязателен: без него запись считается «не опубликованной»
  (`CHECKSUM_REQUIRED`), а при расхождении установка прерывается
  (`CHECKSUM_MISMATCH`).

Пересобрать индекс под другой хостинг (свой CDN, GitHub Releases):

```bash
# пакет + индекс в корне репозитория
python tools/pack.py --base-url https://cdn.example.com/plugins

# вариант с GitHub Releases: приложить zip к релизу v1.0.0
python tools/pack.py --base-url https://github.com/kafder100/RustWipe/releases/download/v1.0.0
```

`pack.py` сам проверяет результат через `tools/check_index.py` и печатает URL
индекса для панели.

### 4.3a. Как выпустить обновление

```bash
# 1) поднять version в rust-autowipe/plugin.json (например 1.0.2) и в объекте
#    manifest в конце rust-autowipe/frontend/frontend.mjs; добавить раздел
#    «## 1.0.2» в начало CHANGELOG.md
# 2) пересобрать пакет и индекс (pack.py сам запустит check_index.py)
python tools/pack.py
# 3) проверить локально
node tools/test.mjs && node tools/ui-smoke.mjs && node tools/review/run.mjs
# 4) отправить в отдельную ветку и открыть pull request в main
git switch -c release-1.0.2
git add -A && git commit -m "release: rust-autowipe 1.0.2"
git push -u origin release-1.0.2
# 5) CI зелёный — слить pull request в main: с этого момента панели видят версию
# 6) метка на коммите из main — workflow release.yml создаст GitHub Release
git switch main && git pull
git tag v1.0.2 && git push origin v1.0.2
```

`pack.py` (через `check_index.py`) упадёт, если sha256 в индексе не совпадёт с
архивом, версия в `plugin.json`, `index.json`, `CHANGELOG.md`, во frontend и в zip
разойдётся, в zip попадёт запрещённая запись или код в zip будет не тот, что в
`rust-autowipe/`. Сборка воспроизводимая: постоянные даты и права записей, порядок по
имени. Уже собранный пакет той же версии сравнивается по содержимому: те же файлы —
пакет и sha256 не меняются (даже если другой zlib сжал их иначе), другие — ошибка,
пока не поднимете версию.

**CI не отзывает выпуск задним числом.** Панели берут пакет по `index.json` из
ветки `main`, как только коммит туда попал (с поправкой на 5 минут кэша). CI
запускается уже после push: он покажет ошибку, но не вернёт панелям прошлую версию.
Поэтому сломанную версию останавливает только порядок работы — проверки локально
и pull request с зелёным CI до слияния в `main`. Чтобы это не зависело от памяти,
защитите ветку `main` в настройках репозитория GitHub (Settings → Branches или
Rules): слияние только через pull request, обязательные проверки CI (задачи из
`ci.yml`), без force-push. `push_to_github.mjs` обновляет ветку напрямую через API —
для выпуска запускайте его с `--branch release-1.0.2` и открывайте pull request.

Что делает `release.yml` по метке `vX.Y.Z`: прогоняет те же проверки, что CI;
проверяет, что метка совпадает с `version` и стоит на коммите из `main`; пересобирает
пакет (`pack.py` без `--allow-repack`) и требует, чтобы `dist/` и `index.json`
совпали с коммитом; создаёт GitHub Release. Уже опубликованный файл выпуска не
заменяется: он сверяется по sha256, и другой файл — ошибка.

### 4.4. Полезные API-вызовы

```bash
# включить (после принятия дисклеймера в UI проще)
curl -X POST https://panel.example.com/api/plugins/rust-autowipe/enable \
  -H "Authorization: Bearer $KEY" -H 'Content-Type: application/json' \
  -d '{"enabled":true,"safety":{"disclaimerVersion":"1"}}'

# перечитать код с диска
curl -X POST https://panel.example.com/api/plugins/rust-autowipe/reload \
  -H "Authorization: Bearer $KEY"
```

Роуты самого плагина — для тех, кто зовёт их скриптами. Все они под
`/api/plugins/rust-autowipe/servers/:serverId/`:

| Роут | Что важно |
|---|---|
| `POST profiles/:id/run` | тело — `{ "dryRun": true }` (проверка), `{ "dryRun": false }` или пустое (боевой вайп); другое (строка `"true"`, лишнее поле, параметр в адресе) — 400 `BAD_RUN_REQUEST` |
| `POST profiles`, `PUT profiles/:id` | флаги (`enabled`, `options.stopServer`, `startServer`, `dryRun`, `warnChat`) — только `true`/`false` (или строки `"true"`/`"false"`); неверное поле — 400 с причиной. `PUT` принимает `expectedUpdatedAt`: профиль менялся с тех пор — 409 `PROFILE_CHANGED` |
| `GET profiles` | у профиля есть ещё `running`, `lastSkippedAt`, `lastSkipReason`, `catchUpOf` (плановый срок, который догоняется после отсчёта) и `lastCheckAt`, `lastCheckStatus`, `lastCheckId`, `lastCheckError` |
| `POST profiles/:id/preview` | `paths`, `directories` (какие из путей — папки), `skipped` (`[{ path, reason }]`), `truncated`, `limitHit` (`{ kind, detail }`, `kind` — `listings`, `matches` или `depth`) |
| `GET map-variables` | значения — только у переменных с `SEED` или `SIZE` в имени, у остальных одно имя |

Коды 409: `SERVER_BUSY` — на сервере уже идёт вайп; `PROFILE_RUNNING` — профиль выполняется,
менять и удалять его нельзя; `PROFILE_CHANGED`. В событии `rust-autowipe:run-completed`
есть поле `dryRun` (у проверки `deleted` — сколько было бы удалено).

## 5. Настройка после установки

### 5.1. API-ключ (обязательно для остановки/запуска)

Плагин не может останавливать сервер сам — он вызывает REST API панели. Нужен ключ:

1. **Admin → Access Control → API Keys → Create API Key**.
2. Права ключа: `server.read`, `server.start`, `server.stop`, `server.startup`
   (последнее — для записи `WORLD_SEED`/`WORLD_SIZE`) и `console.write`
   (команды после запуска и предупреждения в чат). `server.read` обязателен: им плагин
   читает статус сервера, имя шаблона (проверка «только Rust», `GET /api/servers/:id`)
   и список доступа сервера (проверка субпользователей, `GET /api/servers/:id/permissions`).
   Без ключа (или без этого права) субпользователи получают отказ, а админ и владелец
   сервера работают.
3. Для сообщений в чат нужен ещё **`admin.write`**: консольный роут панели
   (`POST /api/servers/:id/console/command`) разрешает запись владельцу сервера или
   администратору, поэтому не-админский ключ получает `403` даже с `console.write`.
   Если сервер принадлежит другому пользователю — без `admin.write` предупреждения
   и `commandsAfter` работать не будут. То же со списком доступа сервера: его панель
   отдаёт владельцу сервера, тем, кто в этом списке, и админу. Поэтому для
   субпользователей на чужих серверах ключу тоже нужен `admin.write`.
4. Скопировать ключ (показывается один раз).

Затем **Admin → Extensions → Plugins → Rust AutoWipe → Settings**:

| Поле | По умолчанию | Смысл |
|---|---|---|
| `panelUrl` | пусто | Базовый URL панели для power-команд. Пусто → `http://127.0.0.1:<PORT>` (внутри контейнера backend). Если backend слушает не 3000 — укажите `http://127.0.0.1:3000` или публичный URL. Адрес должен вести прямо на API панели: переходы (redirect) при проверке доступа плагин не выполняет |
| `apiKey` | пусто | API-ключ из шага 1 |
| `schedulerEnabled` | `true` | Фоновый планировщик. Выключатель действует сразу, перезапуск не нужен |
| `catchUpMinutes` | `120` | Сколько минут после планового времени ещё можно запустить пропущенный вайп. `0` — не догонять, но вайп в свою минуту идёт |
| `stopTimeoutSec` | `300` | Сколько секунд ждать статуса `stopped` после команды остановки |
| `startTimeoutSec` | `240` | Сколько секунд ждать статуса `running` после запуска |
| `dryRun` | `false` | Глобальный режим проверки для всех профилей: ничего не удаляется, отсчёта в чате нет |
| `wipeWarningEnabled` | `true` | Предупреждения в чат перед плановым вайпом |
| `wipeWarningMinutes` | `5` | За сколько минут начинать предупреждения |
| `wipeWarningText` | `Вайп сервера через {minutes} мин` | Текст, `{minutes}` → число минут |

Проверка: вкладка **Rust AutoWipe** → чип в шапке должен стать зелёным «API-ключ задан»,
кнопка **«Диагностика»** дергает `GET /api/servers` вашим ключом, а **«Тест предупреждения»**
в карточке профиля отправляет одно сообщение в чат сервера (сразу видно, если ключу
не хватает прав).

### 5.2. Права для пользователей панели

Кто что может:

| Кто | Смотреть вкладку | Менять профили и выбирать файлы | Запускать вайп и проверку |
|---|---|---|---|
| админ панели (`admin.write` или `*`) | да | да | да |
| владелец сервера | да | да, без ролей плагина | да, без ролей плагина |
| субпользователь этого сервера | да | с ролью `rust-autowipe.manage` | с ролью `rust-autowipe.run` |
| все остальные | нет | нет | нет |

Плагин объявляет роли (появятся в **Admin → Access Control → Roles → Plugins**):

- `rust-autowipe.manage` — создавать/менять/удалять профили (включая списки путей!),
  выбирать файлы в пикере, кнопки «Диагностика» и «Определить из шаблона»;
- `rust-autowipe.run` — кнопки «Вайп сейчас», «Проверка» и «Тест предупреждения».

Субпользователь — тот, кто есть в списке доступа этого сервера в панели и у кого там есть
`server.read`. Список плагин читает своим API-ключом (§5.1); без ключа субпользователи
получают отказ. Глобальная роль с `server.read` без доступа к этому серверу не пропускает.
Доступ через роль, выданную на сервер, или через права на ноду плагин тоже не засчитывает:
таких людей нет в списке доступа сервера.

Права владельца без ролей действуют, когда он вошёл в панель. Запрос с API-ключом
(например, из скрипта) ограничен правами ключа: владельцу сервера тогда нужна роль
плагина в правах ключа. Cookie пользователя плагин никуда не пересылает.

> `rust-autowipe.manage` — это право менять то, что будет удалено. Выдавайте только тем,
> кому доверяете удаление файлов серверов.

## 6. Работа с Rust: что и зачем удалять

В каталоге сервера Rust Dedicated файлы лежат в `server/<identity>/`
(identity задаётся `SERVER_IDENTITY` в шаблоне, часто это `rust` или UUID):

| Файл / каталог | Что это |
|---|---|
| `proceduralmap.<...>.map`, `.sav` | сохранение мира; в имени есть протокол-версия, поэтому нужны маски |
| `player.blueprints.*.db` | чертежи игроков |
| `player.deaths.*.db`, `player.states.*.db` | смерти/состояния |
| `sv.db`, `sv.db-wal`, `sv.db-shm` | общая база сервера (игроки, сущности) |
| `cfg/server.cfg` | настройки сервера — **не удалять** |
| `oxide/data`, `carbon/data` | данные плагинов Oxide/Carbon |

Пресеты плагина:

| Пресет | Пути | Что получается |
|---|---|---|
| Карта (map wipe) | `/server/*/proceduralmap.*.map`, `/server/*/proceduralmap.*.sav`, `/server/*/proceduralmap.*.sav.?`, `/server/*/proceduralmap.*.sav.??` | новый мир вместе с его запасными копиями, блюпринты живы |
| Карта + блюпринты | предыдущее + `/server/*/player.blueprints.*.db`, `/server/*/player.blueprints.*.db-wal`, `/server/*/player.blueprints.*.db-shm` | обычный месячный вайп |
| Данные игроков | `/server/*/player.*.db`, `/server/*/player.*.db-wal`, `/server/*/player.*.db-shm` (исключение `/server/*/cfg`) | сброс игроков без смены карты |
| Полный вайп | `/server/*` с исключением `/server/*/cfg` | новый мир, новая база, новые игроки, `server.cfg` сохранён |
| Данные Oxide | `/oxide/data/*` | чистые данные плагинов Oxide |
| Данные Carbon | `/carbon/data/*` | то же для Carbon |

Запасные копии сохранения (`.sav.1`, `.sav.2` … — их число задаёт `server.savebackupcount`)
относятся к старому миру и удаляются вместе с ним. Маски `.sav.?` и `.sav.??` берут только
номера 1–99: ручная копия вроде `.sav.bak` остаётся. `-wal` и `-shm` — служебные файлы
базы `.db`, они удаляются вместе с ней. Пресет заполняет пути только при нажатии: в уже
сохранённом профиле новых масок нет. Чтобы добавить их, откройте профиль, нажмите кнопку
пресета ещё раз (добавятся только недостающие пути) и сохраните.

Сид и размер карты — это переменные шаблона `WORLD_SEED` и `WORLD_SIZE`, которые
подставляются в startup Rust (`+server.seed {{WORLD_SEED}} +server.worldsize {{WORLD_SIZE}}`).
Плагин меняет их через API панели перед запуском; если яйцо захардкодило значения,
смена сида не сработает — поправьте startup шаблона.

Рекомендуемый сценарий под Force Wipe:

1. Профиль «Карта + блюпринты», тип **«N-й день недели месяца»**, `первый`, `четверг`, время —
   за 1–2 часа до обновления Facepunch (например 17:00 в поясе профиля).
2. Остановка/запуск — включены.
3. В настройках сервера/шаблона обновление игры — отдельно (плагин не обновляет Steam-сборку).

Если сервер сам не создал файлы (например, только что установлен), предпросмотр покажет
«Ничего не найдено» — это нормально: нечего стирать. Вайп в таком случае закончится
ошибкой «Ни один путь не найден», а сид и размер карты всё равно сменятся.

## 7. Как устроен UI и почему так

Вкладка серверная: панель передаёт компоненту `{ serverId }`, а плагин строит интерфейс
только вокруг этого сервера (без выбора сервера и без панельного списка).

Что есть во вкладке:

- **Кнопки карточки профиля:** «Проверка» (проверочный прогон), «Что будет удалено»,
  «Тест предупреждения», «Изменить», «Выключить»/«Включить», красная «Вайп сейчас»
  в конце ряда и «Удалить». Пока запрос в пути или профиль выполняется, его кнопки
  неактивны, а вкладка сама обновляет состояние, пока прогон не кончится.
- **Окна подтверждения.** Перед боевым вайпом — окно со списком последствий (сервер
  остановится, что удалится, вернуть нельзя, что будет с картой, запустится ли сервер)
  и кнопкой «Отмена». Если включена «только проверка», окно так и пишет: ничего не
  удалится. Удаление профиля — тоже через окно «Удалить профиль?».
- **Карточка** показывает отдельно «последний вайп: ок/ошибка» и «Проверка: ок/ошибка,
  дата», метку «только проверка», «Не запланирован: профиль выключен» (или «планировщик
  выключен») и «просрочен», если время прошло, а вайпа не было. Даты — в поясе профиля
  (без пояса — в поясе панели), с учётом перевода часов.
- **Редактор.** Путь вручную — поле и «Добавить» под списком «Что удалять»; если в поле
  остался путь, «Сохранить» попросит нажать «Добавить». У исключений — своё поле,
  «Добавить» и «Выбрать в файлах…»; текст из поля исключений добавляется и при
  «Сохранить». Пустые поля (время, число месяца, интервал, размер, сид) не подменяются
  значениями по умолчанию — «Сохранить» просит их заполнить. У «каждые N дней» после
  сохранения в поле «Точка отсчёта» видна дата, от которой идёт серия.
- **Выбор в файлах.** Имена со `*`, `?` и `[` сохраняются буквально: `[*]`, `[?]`, `[[]`.
  Перед добавлением папки (или маски «всё внутри») — окно: папка удаляется целиком,
  со всем содержимым. В корне сервера «Добавить текущий каталог» и «всё внутри» неактивны.
- **Esc** закрывает окна. Редактор с несохранёнными правками по Esc и по кнопкам
  «Закрыть» и «Отмена» спрашивает «Закрыть без сохранения?», а при обновлении страницы
  спрашивает браузер. Если профиль за это
  время изменили (другая вкладка, другой админ или прошёл вайп), «Сохранить» покажет
  сообщение и кнопку «Загрузить новую версию».
- **История прогонов:** столбец «Источник» (расписание или вручную); значок «идёт» у
  вайпа, который ещё не закончился, и «прерван» у оборванного падением панели; у
  проверки — «проверка: ок» и «было бы N»; на узком экране — строками.
- **Пропущенный плановый вайп** виден на карточке профиля: «Пропущен: дата — причина». Время — в поясе профиля,
  пояс подписан, если он не совпадает с поясом панели.
- **Права** в шапке: «Только просмотр» — только если нельзя ни менять, ни запускать;
  иначе «Можно запускать, нельзя менять профили».

Маркетплейс-плагин грузится как `frontend/frontend.mjs` — **самодостаточный бандл**.
Панель не даёт ему свой React: в бандле своя копия React, и любой хук падает с
«null dispatcher». Компилировать UI в образ панели (путь официальных плагинов) для
самодельного плагина неудобно.

Решение в этом плагине: компонент-обёртка отдаёт **один `div` с `ref`**, а в него
монтируется обычный DOM-интерфейс. Элемент React собирается вручную по форме React 19
(`$$typeof: Symbol.for('react.transitional.element')`, `ref` в `props`) — это ровно то,
что производит `React.createElement` в 19.x, поэтому панель рендерит обёртку без своей копии
React в бандле.

Плюсы: ноль зависимостей, полный контроль над интерактивностью (пикер, модалки, формы).
Минус: если панель переедет на React 20 с другим символом элемента, обёртку нужно будет
поправить (одна строка `Symbol.for(...)`); сам UI при этом не меняется.

CSS инжектится один раз (`<style id="rust-autowipe-styles">`; после обновления плагина
«на лету» стили заменяются новыми), все классы с префиксом `rw-`. Цвета, скругления и шрифт
вкладка берёт у панели (акцент — цвет панели), своего фона и отступов у неё нет, поэтому
она выглядит как панель и в тёмной, и в светлой теме. Раскладка подстраивается под ширину
вкладки, на телефоне окна занимают весь экран.

Списки путей в редакторе профиля управляемые: `⠿` — перетаскивание мышью (линия вставки
показывает, куда встанет строка), `↑` / `↓` — сдвиг на одну позицию, `✎` — правка по месту
(`Enter` — сохранить, `Esc` — отмена, уход фокуса тоже сохраняет), `⧉` — дубликат под
исходной строкой, `×` — удаление. История прогонов раскрывает каждый шаг: локальное время
с миллисекундами, длительность фазы, полный текст и метрики; прогоны до 1.3.0 показываются
упрощённо (без `data`).

## 8. Безопасность и ограничения

- **Удаление необратимо.** Перед первым боевым вайпом сделайте бэкап сервера
  (панель → Backups) и прогоните профиль в режиме **dry-run** (кнопка «Проверка»).
- Плагин держит `files.write`: файловый туннель сам не проверяет владельца, поэтому плагин
  на каждом роуте проверяет доступ к серверу (админ, владелец или субпользователь из
  списка доступа сервера). Не давайте роль `rust-autowipe.manage` недоверенным.
- Ссылку в середине пути и точку монтирования плагин не видит (§2, «Выбор каталогов и
  файлов»): что за ними, удалится как обычные файлы.
- Планировщик глобальный: он выполняет профили всех серверов, даже если вкладка открыта
  на одном из них. Профиль привязан к своему `serverId` и чужие файлы не трогает.
- Смена сида/размера работает только если startup шаблона подставляет `{{WORLD_SEED}}` /
  `{{WORLD_SIZE}}`; значения сохраняются в сервере и действуют до следующего вайпа.
- API-ключ хранится в конфиге плагина (поле типа `password`) и виден только админам
  в UI панели; но он лежит в БД панели в открытом виде — обращайтесь с ним как с секретом.
- Пакет и его sha256 панели берут из одной ветки `main` этого репозитория. sha256
  защищает от файла, испорченного при скачивании, но не от подмены: кто может писать
  в `main` (или завладел токеном с таким правом), тот выложит панелям любой пакет,
  а подписи пакетов Catalyst не проверяет. Защитите ветку `main` (§4.3a), включите
  двухфакторный вход в GitHub и выдавайте токены публикации с минимальными правами
  на один репозиторий. Токен (`.github-token`) и `.env` не кладите в git — они
  в `.gitignore`, а `push_to_github.mjs` их не отправляет.
- Плагин не делает бэкапов и не обновляет игру: это отдельные задачи панели.
- `catchUpMinutes` защищает от «вайпа через сутки после сбоя панели» — при опоздании больше
  окна запуск пропускается, причина остаётся в профиле.
- Приостановленный в панели сервер плагин не вайпает и не проверяет. На `error`/`crashed`
  удаление выполняется (процесс уже мёртв); запуск после вайпа ждёт `running`, а если не
  дождался — в истории ошибка «Сервер не дошёл до running».
- Планировщик живёт в процессе backend: при выключенном плагине и при остановленной панели
  расписание не работает. Несколько реплик backend одновременно запускать нельзя —
  каждый процесс будет считать себя планировщиком.

### Чего в плагине нет

- **Окна предупреждений на профиль** — окно (`wipeWarningMinutes`) и текст задаются
  настройками плагина; у профиля есть только выключатель `options.warnChat`.
- **Бэкапа перед вайпом**: делайте штатным бэкендом панели (Backups) или отдельной задачей.
- **Планировщика вне процесса панели**: тик живёт в backend и останавливается вместе с панелью.

## 9. Диагностика

| Симптом | Что проверить |
|---|---|
| Вкладки нет в карточке сервера | плагин включён? шаблон сервера матчится `namePattern` из `templateFilter` (по умолчанию `rust`)? перезагрузите страницу с Ctrl+F5 |
| Вкладки нет ни на одном сервере | плагин включён (`GET /api/plugins` → `enabled: true`)? в манифесте есть `frontend`, а в пакете — `frontend/frontend.mjs`? |
| «Нет доступа к этому серверу» | вы не владелец и не админ. Субпользователь должен быть в списке доступа этого сервера с `server.read`. Если в тексте «не задан API-ключ» или «не удалось прочитать список доступа» — плагину нужен API-ключ, который видит этот список (§5.1) |
| «Сервер не Rust (шаблон «…»)» | в имени шаблона нет `rust`. Если это всё-таки Rust — поправьте `namePattern` во frontend и `RUST_TEMPLATE` в `backend/index.js` (§2) |
| «Сервер приостановлен» | снимите приостановку сервера в панели: до этого плагин его не вайпает и не проверяет |
| «Недостаточно прав: нужен rust-autowipe.manage» | роль пользователя не содержит это право (Admin → Roles → Plugins) |
| «Цель …: нельзя удалять всё содержимое корня…» или «Цель … охватывает всё содержимое корня…» | в цели нет ни одного обычного символа (`/*`, `/**` …): укажите конкретные папки, например `/server/*`. Удалить такой профиль можно и без правки |
| «Раскрытие путей упёрлось в предел …: вайп отменён до удаления» | больше 500 путей, 250 чтений папок или глубже 8 уровней. Сузьте маски или исключение с `**`, разделите профиль на несколько |
| «Вайп не начат: … похоже на ссылку (права 777)» или «… странное имя» | ссылку плагин не трогает, и пока такой путь среди найденного, вайп не идёт. Если это обычный файл или папка — смените права (644/755) или уберите путь из профиля; странное имя удалите вручную |
| «Не удалось записать переменные карты» | у API-ключа нет `server.startup`; либо значение не проходит правило шаблона (в тексте ошибки будет поле и правило) |
| Сид не меняется после вайпа | в startup шаблона нет `{{WORLD_SEED}}` (или имя переменной другое) — проверьте кнопкой «Определить из шаблона» и командой запуска в шаблоне |
| «Нет API-ключа» | Settings → `apiKey`; «Диагностика» покажет текст ошибки |
| `401`/`403` в диагностике | у ключа нет `server.read` / `server.start` / `server.stop`; ключ от другой панели |
| `ECONNREFUSED 127.0.0.1:3000` | backend слушает другой порт: задайте `panelUrl` (например `http://127.0.0.1:3000`) или публичный URL |
| «Сервер не остановился: таймаут» | увеличьте `stopTimeoutSec`, посмотрите консоль сервера |
| «Сервер не дошёл до running» | сервер не запустился за `startTimeoutSec` или упал при запуске: смотрите консоль сервера; если он просто долго грузится — увеличьте `startTimeoutSec` |
| «Агент не отвечает: 3 удаления подряд без ответа — удаление остановлено» | нода или агент недоступны: проверьте ноду в панели. Сервер, остановленный плагином, поднимается |
| «Ни один путь не найден» | сервер ещё не создал файлы либо неверная маска; проверьте предпросмотром. Сид и размер (если их смена включена) при этом уже сменились; сервер, остановленный плагином, поднят |
| «Не удалось записать начало прогона в историю …» | база панели не отвечает: вайп не начат, сервер не тронут. Смотрите логи backend |
| «Прогон прерван: панель или плагин перезапустились …» | панель упала или перезапустилась посреди вайпа. Проверьте сервер и файлы вручную: список удалённых путей может быть неполным. Если сервер остановил плагин, он отправил команду запуска |
| `409` «Профиль изменён в другом месте» | профиль изменили в другой вкладке, другой админ или прошёл вайп: нажмите «Загрузить новую версию» и внесите правки заново |
| `409` «… уже идёт вайп …» или «… выполняется …» | на сервере идёт вайп: дождитесь его конца. Пока профиль выполняется, его нельзя менять и удалять |
| Профиль «висит» в «выполняется» | вайп ещё идёт: смотрите `docker compose logs -f backend \| grep rust-autowipe`. Выключение и перезагрузка плагина его не прерывают. Если backend перезапускали посреди вайпа, при включении плагина прогон закроется как прерванный; незакрытая запись о прогоне держит сервер не дольше 6 часов |
| Плагин не найден после копирования | каталог должен называться `rust-autowipe`, внутри — `plugin.json`; `docker compose logs backend \| grep -i plugin` |
| Ошибка `catalystVersion` | в манифесте `>=1.80.0`; обновите панель или поправьте поле |

Маркетплейс:

| Симптом | Что проверить |
|---|---|
| Плагина нет в Marketplace | в **Marketplaces** источник добавлен и включён; URL открывается в браузере и отдаёт JSON; подождите 5 минут кэша и нажмите обновление |
| `HTTP 404` при чтении индекса | `index.json` закоммичен в `main`; откройте `https://raw.githubusercontent.com/kafder100/RustWipe/main/index.json` |
| «Not published» / нельзя нажать Install | у записи в `index.json` нет `sha256` — пересоберите `python tools/pack.py` |
| `CHECKSUM_REQUIRED` | установка через API без sha256: возьмите дайджест из `index.json` |
| `CHECKSUM_MISMATCH` | архив и индекс разъехались: `python tools/check_index.py`, затем пересобрать и запушить |
| `check_index.py`: «собран не из этих исходников» | код в `rust-autowipe/` поменялся, а пакет — нет: поднимите `version` (plugin.json, frontend, CHANGELOG.md) и пересоберите `python tools/pack.py` |
| `FORBIDDEN_HOST` / `INSECURE_PROTOCOL` | `downloadUrl` должен быть `https://` и публичным (raw.githubusercontent.com подходит) |
| Установилась старая версия | кэш индекса 5 минут + обновите список; проверьте `version` в `index.json` |
| `UNSAFE_ENTRY` / `BLOCKED` при распаковке | в zip попал файл вне allowlist (`src/`, `dist/`, `node_modules/`) — пересоберите `pack.py` |

Логи: `docker compose -f /opt/catalyst/catalyst-docker/docker-compose.yml logs -f backend`.

## 10. Разработка и тесты

```bash
# тесты backend-логики (расписание, маски, прогон вайпа на моках)
node tools/test.mjs

# дымовой тест UI (DOM-шим + мок fetch)
node tools/ui-smoke.mjs

# вёрстка строки пути: автономная страница + замер зазоров через headless Chrome
node tools/preview-paths.mjs .dsh-preview-paths.html

# пересобрать пакет и индекс (base-url уже указывает на этот репозиторий)
python tools/pack.py

# только проверка: схема plugin.json, index.json, sha256, состав zip
python tools/check_index.py

# тесты ревью (tools/review/*.test.mjs), каждый файл — отдельным процессом
node tools/review/run.mjs
```

CI (`.github/workflows/ci.yml`) на каждый push в `main` и на каждый pull request
запускает `test.mjs`, `ui-smoke.mjs` и тесты ревью на Node 22 (на нём работает backend
Catalyst) и Node 24, каждый раз в трёх часовых поясах: `UTC`, `Europe/Moscow`,
`America/New_York` — профиль без своего пояса считается в поясе процесса панели.
Упавший вариант не останавливает остальные. `check_index.py` идёт отдельной задачей.

Итерации на живой панели:

1. скопировать файлы в контейнер (`docker cp`);
2. `POST /api/plugins/rust-autowipe/reload`;
3. обновить страницу панели (фронтенд кэшируется с `?v=<version>`, при правке без смены
   версии — Ctrl+F5).

Версию плагина поднимайте при изменениях манифеста или прав: смена версии/прав требует
повторного принятия дисклеймера.

## 11. Чек-лист первого запуска

- [ ] Плагин установлен и включён, вкладка **Rust AutoWipe** открывается в карточке Rust-сервера
- [ ] Создан API-ключ (`server.read`, `server.start`, `server.stop`; для карты — `server.startup`, для чата — `console.write` и `admin.write`), вставлен в Settings
- [ ] «Диагностика» — зелёная
- [ ] Создан профиль: сервер, расписание, пресет, исключение `/server/*/cfg`
- [ ] «Что будет удалено» показывает ожидаемые пути; папки помечены, «Пропущено» пусто или понятно почему
- [ ] «Проверка»: в истории «проверка: ок», в шагах — «режим проверки»; на карточке — «Проверка: ок»
- [ ] Бэкап сервера сделан
- [ ] «Вайп сейчас» → окно подтверждения → сервер остановился, файлы удалились, сервер поднялся (`running`)
- [ ] «Следующий запуск» на карточке профиля — ожидаемая дата
